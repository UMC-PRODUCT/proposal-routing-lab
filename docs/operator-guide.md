# 제안 운영 안내

제품·기능 개선 및 Design System 제안을 같은 Issue에서 연결·결정·수락합니다. 책임 배정 정본은 [registry/ownership.yml](../registry/ownership.yml), 읽기용 표는 [Ownership Registry](ownership-registry.md)입니다. 조직 임명권은 기존 DRI 체계를 따르며 부총괄의 기록 관리가 모든 제품 결정의 승인권이 되지는 않습니다.

## 담당자 연결

등록된 제품은 유효한 책임자에게 바로 연결합니다. Assignee는 결정 담당자입니다. 대상 불명확·미등록·충돌은 부총괄, 부재 시 총괄이 연결합니다. 미배정 요청의 연결 담당자는 봇 댓글에 별도로 표시합니다. 플랫폼 미등록 영역을 임의의 PM에게 배정하지 않습니다.

현재 결정 담당자 또는 예외 담당자가 봇 안내에 따라 같은 Issue에 작성합니다.

```text
/연결 <Registry 책임 ID>
사유: 범위를 다시 확인한 이유
```

이 명령은 유효한 Registry 책임으로 연결할 뿐 새 역할을 임명하지 않습니다.

## 결정과 실행 수락

담당 DRI는 봇 댓글의 문안을 복사합니다. `결정`은 `검증 진행`, `실행 진행`, `보류`, `종료` 중 하나입니다. 첫 줄은 정확히 `## 결정`이어야 합니다.

```text
## 결정
결정: 실행 진행
이유: 사용자가 완료 여부를 확인하기 어렵다
범위: 완료 안내 화면
다음 행동: 안내 개선안을 작성한다
실행 담당자: @실제계정
다음 확인일: YYYY-MM-DD
```

`범위`는 선택 필드입니다. 의미 있는 필드 변경은 새 결정 버전을 만들며 공백·형식만 바꾸면 유지합니다. 봇이 보여주는 실제 버전을 그대로 복사해 실행 담당자가 작성합니다.

```text
/수락 D-댓글ID-해시
실행 작업: https://github.com/OWNER/REPO/issues/NUMBER
```

`/수락`과 작업 링크를 제출하는 것은 **해당 결정 범위와 작업 내용을 본인이 확인하고 맡겠다는 뜻**입니다. 명령 안에 다른 설명을 추가하지 말고 필요한 논의는 별도 댓글로 남기세요. Issue 또는 PR URL을 사용할 수 있습니다. 다른 비공개 저장소 링크의 형식만 검사하며 존재·내용·접근 권한을 검증했다고 표시하지 않습니다.

결정자가 직접 실행한다면 `실행 담당자`를 본인으로 지정하고 같은 결정 댓글에 `본인 수락: 예`와 `실행 작업: URL`을 추가할 수 있습니다. 대리 수락·과거 버전 수락·등록/역할 수락 전 행동은 인정하지 않습니다.

보류에는 `이유`, `다음 행동`, `재검토 담당자`, `다음 확인일`을 남깁니다. 보류는 Open으로 유지하며 확인일에 다시 점검합니다. 종료는 담당 DRI의 `결정: 종료`와 `이유`를 남깁니다. 부총괄·총괄의 접수 정리에는 추가로 `종료 분류: 범위 밖` 또는 `종료 분류: 중복`을 기재하며 제품 채택 여부를 대신 결정하지 않습니다.

## 상태 복구와 인계

검증·실행 결정은 본인 수락과 작업 링크까지 갖추면 Closed가 됩니다. 근거 없는 Close는 재오픈합니다. 사람이 완료 Issue를 다시 열면 새 검토 주기를 시작하고, 봇의 오류 교정 재오픈은 기존 주기를 유지합니다.

최신 관측 결정·수락이 삭제되면 과거 기록을 자동 복원하지 않고 재확인을 요청합니다. 봇 댓글은 관측한 근거의 스냅샷입니다. 봇이 보기 전에 삭제된 기록, Write/Admin 권한자의 댓글 변조까지 복원·차단하는 불변 감사 원장은 아닙니다.

PM Acting Lead 임기는 **2026-09-13~11-07**, **11-08 00:00 KST 종료**, 재검토일은 **10-26**입니다. 자동화 개시일·계정 등록 지연으로 연장하지 않습니다. 만료 후 새 배정·결정은 차단하고 미결 목록은 유지합니다. 후임의 역할 수락과 미결 목록 인수 댓글을 Registry에 연결해야 담당자가 갱신됩니다. 기존의 유효한 완료 결정은 보존합니다.

## 기한과 운영 현황

KST 기준 접수일 다음부터 영업일을 셉니다. 주말·Registry 휴일·2026-10-19~24 시험 휴식을 제외합니다. 미배정 연결은 1영업일, 담당자 첫 댓글은 접수 후 3영업일을 기준으로 점검합니다. 10월 16일 접수의 응답 기한은 10월 28일입니다. 직접 합의한 확인일은 원본을 보존하고 휴식일의 알림·경과 판정만 다음 영업일로 이연합니다.

매시간 17분에 Closed를 포함한 전체 Issue를 검사합니다. 라벨은 검색 필터가 아니며 PR·명시한 제어/연습 Issue 번호만 제외합니다. 한 요청의 오류는 격리합니다. 운영 현황에는 마지막 전체 성공 시각, 조회 범위와 실패를 표시하며 불완전한 조회를 0건으로 표시하지 않습니다. 영업일 09:17 이후 첫 성공 전체 검사에서 예외를 하루 한 번 묶어 알립니다. 시험 기간에는 독촉을 보내지 않습니다.

[GitHub 예약 실행](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)은 지연·누락될 수 있습니다. 큐의 순서는 조직상 결정 순서를 보장하지 않으며, 재검사로 현재 기록을 복구합니다. 지표는 접수·배정·첫 응답·수락까지의 경과와 현재 예외 목록이며 실제 수동 작업시간은 추정하지 않습니다.

## 중단과 수동 운영

Repository Actions 변수 `INTAKE_MODE`를 사용합니다.

| 모드 | 동작 |
|---|---|
| observe | 조회와 Actions 보고만 수행. Issue 변경 없음. 기본값. |
| active | 준비 조건을 확인하고 신규 접수·상태 교정·알림 수행. |
| drain | 신규 정상 접수 중단, 기존 요청 검사·인계 유지. |

공통 준비 조건이 사라지면 관찰 모드로 내려갑니다. 책임자들이 모두 만료됐지만 공통 준비 조건이 유효하다면 기존 요청의 인계 점검을 위한 drain으로 내려갑니다. 잘못된 권한 판정·자동 종료를 발견하면 `observe`로 전환하고 실행 중 작업도 운영자가 확인합니다. 변수 변경은 이미 시작한 프로세스를 취소하지 않습니다.

수동 운영에서는 최신 운영 현황·각 Issue의 댓글을 기준으로 미결 목록을 확인하고, 같은 결정·수락 형식으로 기록합니다. 자동 기한·자동 종료가 작동한다고 안내하지 않습니다. 복구 후 observe 전체 검사의 예상 변경을 확인한 다음 active/drain으로 복귀합니다. 쓰기 직전 재조회로 경합을 줄이지만 GitHub의 여러 API 요청을 하나의 원자적 트랜잭션으로 처리하지는 못합니다.

향후 비공개 전환 시 [보호 기능 유지 여부](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)를 먼저 확인합니다. 유지할 수 없다면 observe와 최소 Write 권한의 수동 운영으로 전환합니다. 이미 공개된 복제본·포크는 회수할 수 없습니다.
