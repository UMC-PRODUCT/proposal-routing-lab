# UMC PRODUCT 제안 접수

제품·기능 개선과 Design System에 관한 문제를 제안하고, 담당자의 결정과 실행 인계를 같은 GitHub Issue에 기록합니다. 담당 팀을 외우거나 해결책을 완성하지 않아도 제안할 수 있습니다.

> **현재는 도입 준비 중이며 자동 접수를 시작하지 않았습니다.** 아래는 운영 개시 후 사용할 절차입니다. [운영 현황](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/6)에서 시작 안내를 확인하세요. 열람은 누구나 가능하지만 자동 접수·결정·수락은 계정 등록이 끝난 구성원만 사용할 수 있습니다.

[제안 작성하기](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/new/choose) · [내 제안과 처리 상태 보기](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues) · [제품별 담당자 확인](docs/ownership-registry.md)

## 어떤 제안을 올리나요?

| 제안 종류 | 예시 |
|---|---|
| 제품·기능 개선 | 가입 안내 개선, 공지 찾기 개선, 출석·승인 기능의 불편 해결 |
| Design System | 공통 컴포넌트·토큰·패턴, 플랫폼 간 공통 행동·상태 개선 |

조직의 인사·회의·운영 제도 변경과 일상 개발 작업은 기존 경로에서 다룹니다. 예를 들어 **출석 기능 개선**은 여기서 제안하고, **출석 운영 규칙 변경**은 기존 조직 운영 경로에서 논의합니다.

## 1. 제안을 작성하세요

1. 등록한 본인 GitHub 계정으로 로그인하고 [제안 양식](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/new/choose)을 엽니다. 계정 등록 여부가 불확실하면 접수 운영 담당자인 부총괄에게 확인합니다.
2. **제품·기능 개선** 또는 **Design System**을 고릅니다.
3. **대상·문제·원하는 도움**을 작성하고 제출합니다. 근거·스크린샷·Figma 링크는 선택 사항입니다.

다음은 작성 방법을 보여주는 예시입니다.

| 항목 | 작성 예시 |
|---|---|
| 대상 | 공식 홈페이지·테크 블로그·대외 콘텐츠 |
| 문제 | 모집 안내에서 지원할 수 있는 직군을 찾기 어렵습니다. |
| 원하는 도움 | 직군별 지원 조건을 한곳에서 볼 수 있도록 개선을 검토해주세요. |

대상을 고르기 어렵다면 제품 양식의 **`모르겠음 / 여러 영역에 해당`**을 선택하세요. 연결 담당자가 범위를 확인합니다. Design System 등 담당자 등록이 끝나지 않은 영역은 준비 상태를 안내하며, 다른 PM에게 임의로 배정하지 않습니다.

**제목·본문·댓글·첨부는 공개됩니다.** 실제 사용자 개인정보와 민감한 원본 자료는 기존 비공개 작업에 보관하세요. 제안자 신원은 작성한 GitHub 계정으로 확인하므로 사용자명을 다시 적지 않습니다.

## 2. 같은 Issue에서 담당자와 다음 행동을 확인하세요

자동 접수가 시작되면 봇의 **제안 처리 안내** 댓글에 담당자·현재 상태·다음 행동이 표시됩니다. 보완 요청과 논의도 같은 Issue에서 이어갑니다.

| 상태 | 다음 행동 |
|---|---|
| 검토 중 | 제안자는 빠진 정보를 보완하고, 결정 담당자는 제안을 검토합니다. 미배정이면 연결 담당자가 확인합니다. |
| 수락·인계 대기 | 실행 담당자가 결정 범위와 작업 링크를 확인한 뒤 본인 계정으로 수락합니다. |
| 보류 | 표시된 재검토 담당자와 확인일을 확인합니다. |
| 처리 완료 | 결정 또는 실행 인계가 끝났습니다. 실제 개발 진행·완료는 연결된 작업에서 확인합니다. |

미배정 연결은 다음 영업일까지, 결정 담당자의 첫 응답은 접수 후 3영업일까지를 기준으로 확인합니다. 결정 완료 기한을 뜻하지 않습니다. 접수일 다음 날부터 주말·설정 휴일·시험 휴식 기간을 제외해 계산합니다. 정확한 날짜는 봇 댓글을 확인하세요.

## 3. 결정 또는 실행 담당자로 지정되면 기록을 남기세요

### 결정 담당자

봇 댓글의 결정 문안을 복사해 **새 댓글**에 작성합니다. `검증 진행`, `실행 진행`, `보류`, `종료` 중 하나를 선택하세요. 다음은 실행 진행 결정의 형식입니다. 계정과 확인일은 실제 합의한 값으로 바꿉니다.

```text
## 결정
결정: 실행 진행
이유: 지원 조건을 찾기 어렵다는 문제를 확인했다
범위: 모집 안내의 직군별 지원 조건
다음 행동: 안내 개선안을 작성한다
실행 담당자: @실제계정
다음 확인일: YYYY-MM-DD
```

보류에는 이유·다음 행동·재검토 담당자·확인일이 필요합니다. 종료에는 담당자의 종료 이유가 필요합니다. [보류·종료와 재연결 방법](docs/operator-guide.md)을 확인하세요.

### 실행 담당자

결정 범위와 실행 작업의 내용을 확인하고, 맡기로 했다면 **봇이 보여주는 실제 결정 버전**을 복사해 새 댓글로 수락합니다.

```text
/수락 D-댓글ID-해시
실행 작업: https://github.com/OWNER/REPO/issues/NUMBER
```

위 두 줄에서 결정 버전과 URL을 실제 값으로 바꾸세요. 실행 작업은 GitHub Issue 또는 PR 링크를 사용할 수 있습니다. 설명을 덧붙여야 하면 별도 댓글에 남깁니다.

수락은 지명받은 사람이 본인 계정으로 해야 합니다. 범위가 바뀌면 새 버전에 다시 수락해야 합니다. 비공개 작업 링크도 사용할 수 있지만, 내용을 확인하는 책임은 수락한 사람에게 있으며 봇이 존재·내용·접근 권한을 확인하지는 않습니다. 결정자가 직접 실행하는 경우의 기록법은 [운영 안내](docs/operator-guide.md)에 있습니다.

## 처리가 멈춘 것 같다면

운영 개시 후에도 안내 댓글이 없거나 갱신되지 않으면 [운영 현황](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/6)의 마지막 전체 검사 성공 시각을 확인하고, 해당 제안 링크를 결정 담당자나 부총괄에게 전달하세요. 같은 제안을 반복해서 만들 필요는 없습니다.

2026-10-19~24에는 기한 계산과 독촉 알림을 쉽니다. 운영 중인 영역의 접수·배정·결정·수락은 계속 처리합니다. 예를 들어 10월 16일에 접수했다면 3영업일 응답 기한은 10월 28일입니다.
