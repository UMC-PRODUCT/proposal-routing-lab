# 제안 제출과 처리 흐름

초기 접수·처리·기록은 **GitHub만 사용**합니다. 이 문서는 현재 수동 접수 경로를 먼저 안내하고, 별도로 준비 중인 기존 자동 파일럿 안내를 뒤에 보존합니다. 운영 정본은 워크스페이스의 **`제안-접수-GitHub-초기운영-가이드.md`**입니다. 문서 완성과 실제 운영 시작은 별개이며, 담당 계정·본인 수락·접근권한을 확인한 뒤 시작 시점을 안내합니다.

## 초기 수동 접수 경로: 시작 안내 후 사용

1. **제품·기능 개선 또는 Design System 제안**인지 확인합니다. 조직의 운영 규칙·역할·회의 방식 제안과 팀 내부의 일상 작업은 기존 경로를 사용합니다. 공지·출석·승인 등 운영을 지원하는 제품 기능의 개선은 여기서 받습니다.
2. [수동 접수 양식](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/new?template=manual.yml)을 열어 실제 제안자에 본인 계정을 적고, 문제·근거·원하는 도움을 작성합니다. 현재 양식의 `Discord 원글 링크`는 비워도 됩니다.
3. 연결할 팀을 모르면 `모르겠음`을 선택하세요. 등록한 Issue의 댓글에서 담당자 연결·보완·결정을 확인하고, 실행을 맡기로 하면 같은 Issue에 본인 수락을 남깁니다.

수동 접수 Issue에는 `manual-intake` 라벨을 사용합니다. **자동 담당자 지정·3영업일 자동 기한·결정과 수락의 자동 검증은 없습니다.** 봇의 운영 기록 댓글을 기다리지 말고 [수동 접수 운영 안내](docs/manual-operations.md)의 한국어 결정·본인 수락 흐름을 따르세요. 접수 담당이나 결정권자가 아직 정해지지 않았다면 `미정`으로 남기고 필요한 연결을 요청합니다.

목적팀 PM은 Acting Lead로 해당 기간 Purpose DRI 책임을 맡습니다. 정확한 임기·시작일·Review일은 미정이고 6~8주는 후보입니다. 정상 목적팀 요청을 PM에게 바로 연결하고 미배정·충돌·확인일 경과만 부총괄에게 연결하는 절차는 권고안이며, 실제 예외 담당자와 대행자의 수락은 별도로 확인합니다.

운영 절차 권고안에서는 결정과 실행 담당자의 본인 수락, 실행을 추적할 GitHub Issue/PR 링크가 갖춰지면 **제안 처리 완료**로 정리합니다. 제품 개발 완료를 뜻하지 않습니다. 보류할 때는 이유·확인 담당자·다음 확인일을 남깁니다. 세부 형식과 처리 기준은 운영 시작 전에 합의합니다.

현재는 수동 양식 하나를 사용합니다. 제품·기능과 Design System용 수동 간소 양식을 두 개로 나누는 안과 GitHub 기록 자동집계는 권고 단계로 미구현입니다. Discord 접수·결과 안내 파이프라인도 초기 운영에 포함하지 않으며, 사용 중 필요가 확인되면 검토합니다.

## 기존 자동 접수 파일럿: 별도 활성화 후 사용

아래 내용은 제품·기능 Proposal / Design System Proposal 양식으로 접수하는 기존 파일럿의 안내입니다. **이 파일럿은 현재 실제 접수 전입니다.** [활성화 이슈 #1](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/1)에서 시작 여부와 합의한 접수 기간을 확인한 뒤 사용하세요. 시작 승인 전에 생성한 이슈는 나중에 자동으로 실제 접수 대상에 포함되지 않습니다. 수동 접수 Issue도 자동 전환하지 않습니다.

운영 담당자는 [운영 가이드](docs/operator-guide.md)에서 준비·담당자 지정·종료 절차를 확인하세요. 이후의 상태표와 3영업일 기한, 영문 결정·수락 명령은 수동 접수에는 적용되지 않습니다.

## 어떤 제안을 제출하나요?

| 제안 | 사용할 양식 | 작성할 내용 |
|---|---|---|
| 사용자 문제를 해결하는 제품·기능 개선 | 제품·기능 Proposal | 겪은 문제, 확인한 근거, 가장 작게 검증할 방법 |
| 여러 화면·제품에 적용할 디자인 기준 개선 | Design System Proposal | 공통 행동·상태, 플랫폼별 표현, 컴포넌트·토큰과 기존 화면의 영향 |

팀 내부의 일상 작업은 기존 팀의 작업 목록에 기록합니다. 제안은 실행 담당자가 모두 정해지기 전에도 작성할 수 있습니다. `DRI 의향`은 제안이 진행될 때 실행을 맡을 의향을 묻는 항목이며, 실제 책임 수락은 첫 결정 단계에서 따로 기록합니다.

## 제안 작성하기

1. [제안 양식 선택 화면](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/new/choose)을 엽니다. 접근할 수 없다면 로그인한 GitHub 계정을 확인하고, 파일럿 운영 담당자에게 참여자·접근권한 확인을 요청하세요.
2. 제안 종류에 맞는 양식을 선택합니다. 각 항목의 설명과 예시를 참고해 확인한 사실과 아직 모르는 내용을 구분해 적습니다.
3. 제품 제안의 담당 목적팀을 모르면 `모르겠음`을 선택합니다. Design System의 Figma 자료가 없다면 해당 항목의 안내에 따라 `미존재: 사유`를 적습니다.
4. 필수 항목을 채우고 제출합니다. 생성된 Issue의 주소를 보관하세요. 이후 보완 요청과 결정은 같은 Issue에서 확인합니다.

작성 예: 가입 과정의 문제라면 “가입이 불편합니다”에서 끝내지 말고, 누가 어느 단계에서 막혔는지와 관찰한 근거를 적습니다. 가장 작은 검증에는 바꿔 볼 화면이나 문구, 결과를 확인할 방법을 적습니다. 근거를 이미 모았다면 그 내용을, 아직 수집하지 못했다면 현재 확인하지 못한 점과 수집 계획을 설명하세요. 예시 수치나 사실을 실제 관찰처럼 복사하지 않습니다.

## 제출 후 무엇을 확인하나요?

자동 처리가 끝나면 Issue의 **제안 운영 기록** 댓글을 확인합니다. 처음 제출했을 때 댓글이 없으면 잠시 뒤 새로고침하고, 계속 나타나지 않으면 Issue 주소와 함께 운영 담당자에게 알려주세요.

| 표시된 상태 | 다음 행동 |
|---|---|
| 필수 정보 보완 대기 | 제안자가 댓글에 표시된 누락 항목을 Issue 본문에서 수정합니다. 처음 유효하게 접수되기 전에는 첫 결정 기한을 계산하지 않습니다. |
| 첫 결정 대기 | 결정권자와 첫 결정 기한을 확인합니다. 결정권자가 아직 없으면 운영 담당자가 지정할 차례입니다. 실행 담당자로 지명받았다면 결정 내용을 확인하고 아래 수락 절차를 따릅니다. |
| 첫 결정 기록 완료 | 결정 댓글의 이유·다음 행동·담당자를 확인합니다. 지정된 다음 행동을 진행하고 재검토 조건·날짜를 확인합니다. |
| 결정 기록 재확인 필요 | 결정이나 수락 기록이 바뀐 상태입니다. 운영 담당자와 결정권자가 수정 내용을 확인합니다. |
| 비활성·참가자 확인 필요·접수 기간 밖 | 실제 접수 여부를 운영 담당자에게 확인합니다. 새 이슈를 반복해서 만들기 전에 안내를 받으세요. |

첫 결정 기한은 필수 정보가 갖춰진 시점을 기준으로 계산합니다. 기본 설정은 그날의 한국 날짜 다음부터 3영업일째 23:59 KST이며, 주말과 설정한 휴무일을 제외합니다. 본인의 정확한 기한은 Issue 운영 기록에서 확인하세요.

## 실행 책임을 수락하기

결정권자가 제안의 실행을 맡을 사람인 **Proposal DRI**를 제안하면, 해당 결정의 범위와 다음 행동을 먼저 확인합니다. 맡기로 합의한 사람이 같은 Issue에 직접 수락 댓글을 남겨야 합니다. 제안 양식에서 의향을 선택한 것만으로 실행 책임이 확정되지는 않습니다.

명령 작성법과 댓글 ID 확인 방법은 [첫 결정과 책임 수락](docs/operator-guide.md#decision)을 참고하세요. 맡기 어렵거나 범위를 조정해야 한다면 수락 전에 결정권자와 해당 Issue에서 합의합니다.
