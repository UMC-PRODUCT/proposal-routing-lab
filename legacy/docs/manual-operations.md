# GitHub 초기 수동 접수 운영 안내

> 적용: 제품·기능 개선과 Design System 제안의 초기 접수·처리·기록  
> 기록 기준: `manual-intake` 라벨이 붙은 GitHub Issue  
> 운영 정본: 워크스페이스의 **`제안-접수-GitHub-초기운영-가이드.md`**  
> 상태: 운영 문서 정리 완료. 담당 계정·수락·권한 확인과 실제 운영 시작은 별도

초기에는 **GitHub만 사용**해 제안을 받고, 같은 Issue에 결정과 다음 행동을 남깁니다. Discord 접수·알림 파이프라인은 사용 중 필요를 확인한 뒤 검토합니다. 이 문서는 운영 정본을 저장소에서 따라 쓰기 위한 안내이며 조직의 책임·결정권은 3기 조직 운영 모델, DRI 운영체계와 Ownership Registry를 기준으로 확인합니다.

## 1. 무엇을 어디에 등록하나요?

| 접수 대상 | 예 |
|---|---|
| 제품·기능 개선 | 모집 신청 경로 개선, 공지·출석·승인 등 운영을 지원하는 제품 기능 개선 |
| Design System 제안 | 공통 컴포넌트·토큰·패턴, 플랫폼 간 공통 행동과 상태 개선 |

조직 운영 규칙, 역할 배치, 회의 방식에 관한 제안은 이 경로의 대상이 아닙니다. 팀 내부의 일상 작업도 기존 경로를 사용합니다. 운영자의 불편을 다루더라도 제품 기능을 바꾸는 제안과 조직 운영 규칙을 바꾸는 제안을 구분합니다.

1. [현재 수동 접수 양식](https://github.com/UMC-PRODUCT/proposal-routing-lab/issues/new?template=manual.yml)을 엽니다. 실제 제안자에 본인 GitHub 계정을 적습니다.
2. 문제·근거·원하는 도움을 적고 확인하지 않은 내용은 추측이나 미확인으로 표시합니다. 해결책이 완성되지 않았어도 됩니다.
3. 연결할 팀을 선택합니다. 모르면 `모르겠음`을 선택해도 됩니다. 선택만으로 담당자가 자동 지정되지는 않습니다.
4. 현재 양식의 `Discord 원글 링크`는 비워 둬도 됩니다. 생성한 Issue의 댓글에서 보완·결정·실행 책임 수락을 이어갑니다.

현재 `manual.yml`은 GitHub 직접 등록을 지원하는 수동 양식 하나입니다. **제품·기능과 Design System용 수동 간소 양식 두 개로 나누는 안은 권고이며 아직 구현되지 않았습니다.** 기존 제품·기능 Proposal / Design System Proposal 양식은 별도로 준비 중인 자동 파일럿용이므로 초기 수동 접수에는 사용하지 않습니다.

## 2. 담당자와 시작 준비

**목적팀 PM은 Acting Lead로 임시 지정해 해당 기간 Purpose DRI 책임을 수행합니다.** 정확한 임기·시작일·Review일은 아직 정하지 않았고 6~8주는 후보입니다. 직함 선택을 새로운 영구 조직 구조로 해석하지 않습니다.

| 영역 | 현재 정리된 책임과 남은 확인 |
|---|---|
| 네 목적팀 | 해당 팀 PM이 Acting Lead로 Purpose DRI 책임 수행. 실제 GitHub 계정·수락과 적용 기간 확인 필요 |
| Platform Team | 담당자는 OT에서 논의. 아직 확정된 사람처럼 지정하지 않음 |
| Design Platform Team | 결정 담당자의 실명·계정 미정 |
| Infrastructure Team | 담당자 확정. 이 안내에는 GitHub 계정이 확인되지 않아 기재하지 않음 |
| 미배정·충돌 등 예외와 부재 대행 | 실제 책임자·대행자의 수락 미확정. 시작 전 확인 필요 |

수동 Issue의 **Assignee는 해당 제안의 결정 담당자**입니다. 자신의 권한 범위와 해당 건을 맡을 의사를 확인한 뒤 지정합니다. 단순히 등록을 도운 사람을 결정 담당자로 지정하지 않으며, 실행 담당자는 결정·수락 댓글에서 별도로 확인합니다. 담당자가 미정이면 Assignee를 비워 두고 필요한 결정과 다음 확인할 사람·시점을 댓글에 남깁니다.

시작 전 저장소 관리자는 실제 저장소에 `manual-intake` 라벨이 있고, 구성원이 Issue를 작성하고 담당자·실행 담당자가 자신의 계정으로 댓글을 남길 수 있는지 확인합니다. 양식 설정이 라벨 자체를 생성하지는 않습니다. 담당 계정·수락·대행·접근권한과 시작 시점을 확인한 뒤 운영 시작을 안내하며, **문서가 완성됐다는 사실만으로 운영을 시작한 것으로 보지 않습니다.**

## 3. 담당자 연결과 응답 주기 권고

다음은 초기 운영에 적용할 **권고안**입니다. 실제 담당자와 적용 주기를 합의하기 전에는 이미 시행 중인 규칙으로 안내하지 않습니다.

- 정상적인 목적팀 제안은 해당 목적팀 PM에게 직접 연결합니다.
- 미배정, 팀 간 충돌, 합의한 다음 확인일 경과 건만 부총괄에게 연결해 예외 처리를 요청합니다. 예외 책임자와 대행자는 실제 수락을 확인합니다.
- 영업일마다 한 번 미배정·미응답 Issue를 확인하고, 다음 영업일까지 담당자를 연결하며, 등록 후 3영업일 이내 첫 응답을 남기는 안을 권고합니다. 첫 응답은 보완 요청이나 다음 검토 시점 안내일 수도 있으며 최종 결정이나 개발 완료 약속이 아닙니다.

위 주기는 **현행 자동 SLA가 아닙니다.** 지금은 자동 담당자 지정·기한 알림·결정과 수락 검증이 없으므로 담당자가 Issue를 확인합니다. 맡을 사람이나 다음 확인일이 정해지지 않은 건은 그 상태를 숨기지 않고 남깁니다.

## 4. 결정·본인 수락·제안 처리 완료

아래 형식과 처리 완료 기준은 운영 정본의 **권고 절차**입니다. 초기 운영을 시작하기 전에 채택 여부를 확인합니다.

결정 담당자가 **자신의 GitHub 계정으로** 같은 Issue에 짧게 기록합니다. 아래 값은 예시이므로 실제 내용으로 바꿉니다.

```markdown
## 결정
- 결정: 검증 진행 / 실행 진행 / 보류 / 종료 중 하나
- 이유: 확인한 근거와 판단 이유
- 다음 행동: 누가 무엇을 할지
- 실행 담당자: @계정 (수락 대기) 또는 없음 (사유)
- 다음 확인일: YYYY-MM-DD 또는 추가 확인 없이 종료하는 이유
```

실행 담당자는 내용을 확인하고 **본인의 계정으로** 다음 댓글을 남깁니다. 다른 사람이 대신 수락하지 않습니다.

```markdown
## 실행 책임 수락
- 대상 결정: 결정 댓글 링크
- 수락한 범위: 내가 맡기로 한 행동과 범위
```

결정 담당자가 직접 실행하면 본인의 결정 댓글에 수락한 범위를 함께 적어도 됩니다. 수락 뒤 책임이나 범위를 바꾸려면 새 결정과 해당 담당자의 새 수락을 남깁니다. 이전 기록을 지우거나 수락 댓글 시각을 맞추기 위해 반복 수정하지 않습니다.

| 결과 | 정리 기준 |
|---|---|
| 검증·실행 진행 | 결정, 실행 담당자의 본인 수락, 실행을 추적할 GitHub Issue/PR 링크가 갖춰지면 **제안 처리 완료**로 정리합니다. 이후 진행은 연결한 작업에서 관리합니다. |
| 보류 | 이유·다음에 확인할 담당자·날짜를 남기고 재확인 대상으로 유지합니다. 실행할 일이 없으면 실행 담당자와 수락을 억지로 만들지 않습니다. |
| 종료 | 진행하지 않는 이유와 제안자에게 필요한 안내를 남기고 제안 처리를 종료합니다. |

**제안 처리 완료는 제품 개발 완료가 아닙니다.** 실행 담당자와 작업 링크 없이 진행 결정만 남긴 건은 아직 인계가 끝나지 않은 상태입니다.

## 5. 기록으로 확인할 지표 권고 — 미구현

초기에는 GitHub 기록만 이용해 아래 항목을 보는 방안을 권고합니다. 자동 수집·집계·예약 실행은 아직 구현하거나 시작하지 않았으며, 별도 수기 계측 양식을 추가하지 않습니다.

| 확인할 것 | 해석과 한계 |
|---|---|
| 미배정 Issue | 조회 시점에 Assignee가 없는 열린 정식 수동 접수 건. 담당자 확인이 필요하다는 뜻이며 제안 누락으로 단정하지 않습니다. |
| 첫 배정 대기시간 | Issue 생성부터 최초 `assigned` 이벤트까지의 경과시간. 전체 이력이 조회된 경우에 계산하며 담당자가 실제로 읽은 시각은 아닙니다. |
| 첫 사람 댓글 대기시간 | Issue 작성자와 봇을 제외한 첫 댓글까지의 경과시간. 내용상 유효한 첫 응답이나 결정 완료를 자동 판정하는 지표는 아닙니다. |
| 담당 변경 이벤트 | 최초 배정과 이후 `assigned`·`unassigned`를 구분해 확인합니다. 인계 한 번이 두 이벤트일 수 있으므로 변경 횟수를 잘못된 Routing 횟수로 환산하지 않습니다. |

조회 범위·기간·페이지 완료 여부·권한 실패를 함께 남기고, 부분 조회를 전체 0건이나 전체 비율로 표현하지 않습니다. 댓글은 후편집될 수 있으므로 현재 결정 형식이 있다는 사실만으로 최초 결정 시각을 추정하지 않습니다. 형식 관측과 실제 결정권자의 유효한 판단·본인 수락 검증도 구분합니다.

**실제 처리시간은 사람이 손으로 작업한 시간입니다.** Issue·댓글 시각 차이로 추정하지 않으며 별도 타이머나 작업시간 입력을 강제하지 않습니다. 추이를 보려면 조회 결과와 최초 관측 시각을 보존하는 기능이 따로 필요합니다.

## 6. 기존 자동 파일럿과 후속 Discord 연계

- 수동 접수에는 `manual-intake`를 사용하고 자동 파일럿용 `proposal` 라벨을 추가하지 않습니다. 기존 봇의 접수·Routing·기한·결정 검증 대상이 아니므로 봇의 운영 기록 댓글을 기다리지 않습니다.
- 수동 운영을 위해 `PILOT_ACTIVE`나 기존 역할 수락 설정을 바꾸지 않습니다. 기존 자동 파일럿은 별도 준비 상태로 두고 [운영 가이드](operator-guide.md)의 활성화 절차와 구분합니다.
- Discord 접수·결과 안내와 미연결 게시글 수집은 초기 도입 범위에서 제외합니다. GitHub 운영 중 확인한 실제 불편과 필요를 근거로 후속 검토합니다. Discord 원글 링크 필드가 현재 양식에 있다는 사실은 연계가 운영 중이라는 뜻이 아닙니다.
- 새 자동화로 전환할 때는 미완료 Issue·최신 결정·수락·실행 링크·다음 확인 담당자를 인계하고 적용 시작점을 별도로 안내합니다. 수동 기록을 기존 자동 파일럿 표본에 자동 소급 편입하지 않습니다.
